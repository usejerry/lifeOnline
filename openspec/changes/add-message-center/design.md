## Context

动机与范围见 [proposal.md](proposal.md)。后端是 NestJS、TypeORM、MySQL，数据库时间按 UTC 转换，生产 `DB_SYNCHRONIZE=false`，部署文档要求显式 SQL 迁移。现有签到按 Asia/Shanghai 划分日期，并在事务内写签到及成长积分，已有重复签到测试。

`QuestRecordService` 目前只有 accepted/completed/abandoned，通过查询 accepted 阻止第二次接取；完成前会调用地图和天气服务，最终更新仅检查状态。接取记录已有任务名称和目标快照，但没有截止时间。每周主题结束时间不参与接取记录生命周期。

前端是 Vue、Pinia、Vue Router，消息模块尚不存在；`App.vue` 加载页面和底部导航，`DailySignIn.vue` 位于 `ProfileView.vue`，`journey.ts` 管理进行中任务，`RecordsView.vue` 当前仅渲染已完成纪念卡。身份刷新和 `auth:cleared` 事件可以复用。

## Goals / Non-Goals

**Goals:**
- 用现有 MySQL 保存消息和期限，明确消息去重、并发状态转换与跨设备读取的一致性。
- 后台主动生成支线临期消息；接口操作以服务端期限为最终判断，避免后台延迟影响正确性。
- 两个仓库共享本变更下的一套接口契约及验收规则。

**Non-Goals:**
- 不引入 Redis、消息队列、WebSocket 或站外推送；不修改签到奖励和任务推荐耗时含义。
- 不补算旧任务、不创建聊天或运营发布后台、不在本变更实现消息删除和保留期限策略。

## Decisions

### 1. 数据模型和时间来源

`quest_record` 增加可空 `expires_at` 与 `expired_at`，状态增加 `expired`，索引覆盖 `(status, expires_at, id)`。新接取在一次保存中写入 `acceptedAt` 和 `expiresAt = acceptedAt + (durationMinutes + 1440) * 60000`；截止时间本身即接取时快照，旧记录保持 null。`expiredAt` 记录业务截止时刻，实际处理耗时由日志反映。与已有 UTC 存储对齐；服务端时间为权威，临界状态更新使用数据库当前时间，应用与数据库保持时钟同步。

新增 `user_message`：`id`、`user_id`、`type`（daily_sign_in/quest_expiring）、`dedupe_key`、`title`、`content`、`sign_in_date`（可空）、`quest_record_id`（可空）、`deadline_snapshot`（可空）、`created_at`、`read_at`（可空）。唯一键 `(user_id, dedupe_key)`，列表索引 `(user_id, created_at, id)`，未读索引 `(user_id, read_at, id)`。去重键分别为 `sign-in:YYYY-MM-DD`、`quest-expiring:<recordId>`。

消息文案和截止时间快照保持稳定；接口批量读取关联签到日期或接取记录，计算 `businessStatus` 与 `action`，避免每条消息单独查询。readAt 与 businessStatus 独立。关联记录不可用时显示事项不可用并取消操作，不猜测目标。用户删除时清理本人消息，不允许客户端指定消息接收人。

选择持久化消息而非每次临时拼接，因为阅读历史需要稳定标识；不持久化可反推的事项状态，避免签到／任务变更时双写不一致。

### 2. 提醒生成和调度

新增消息同步接口，在用户身份恢复后、站内重新可见、跨北京时间午夜时调用。签到生成只检查当前登录用户今日签到，不扫描全体用户、不补发历史日。唯一键负责跨设备去重；仅捕获对应重复键，其他数据库错误正常返回，重试不重置 readAt。

提取与现有签到一致的北京时间日期工具。同步与签到若并发，按签到检查时观察到的状态确定是否生成；即使检查后立即签到，新消息读取时也显示已签到且不可操作。签到已在检查前成功提交则不生成，提醒创建失败不回滚已经成功的签到。

支线采用 NestJS 调度模块每30秒扫描，启动时执行一次补偿：先批量过期，再扫描 `accepted AND expiresAt > now AND expiresAt <= now + 1h` 并创建提醒。每批限制数量、按截止时间和 id 游标推进，重复实例依靠状态条件与唯一键避免重复。提醒插入事务锁定并重新检查对应记录，保证已经完成／放弃的记录不再生成新消息。正常运行的生成及后台过期目标为60秒以内；站内展示采用刷新获取，不承诺秒级推送。

请求同步也复用当前用户的到期／临期检查以改善可见性。服务恢复时仅补发仍处于临期窗口的记录，已经过期不追发“快过期”；已生成消息保留。此项为正常调度延迟及故障补偿的技术默认值，供本方案审阅。

选择数据库扫描而非仅前端定时器，使用户关闭页面时仍有站内消息历史；相较队列避免增加独立基础设施。调度异常记录错误与批次进度，下次重试，无逐任务常驻计时器。

### 3. 生命周期与并发

到期条件固定为 `now >= expiresAt`，旧记录 null 不参与。active、列表、详情与接取前先协调该用户到期记录；即使后台停止，API 返回的状态与接取名额仍正确。

完成请求在昂贵位置／天气验证前检查期限，最终更新仍必须原子限定 `userId + id + status=accepted + (expiresAt IS NULL OR expiresAt > 数据库当前时间)`，防止外部调用期间跨过截止时间。放弃沿用相同有效期条件；过期更新只允许从 accepted 转换，完成和放弃终态不能被覆盖。更新失败后读取记录区分 `QUEST_EXPIRED` 与既有无效状态错误；若需补记过期，应先提交状态再返回错误，避免抛错使过期事务回滚。控制器沿用失败时删除已上传文件的清理逻辑。

接取事务锁定用户行，协调到期记录后检查是否仍有 active 并插入新记录，避免两个并发接取在名额释放时均成功。接受服务路径都遵循相同锁顺序，地图查询不放在持有用户锁的长事务中。后台仅锁接取记录且不反向获取用户锁，减少死锁机会；遇数据库死锁采用有限重试或可重试错误。

### 4. API 契约

沿用 `/v1` 前缀、现有响应包装和 JwtAuthGuard；用户标识只从认证上下文取得。

| 接口 | 行为与数据 |
| --- | --- |
| `POST /v1/messages/sync` | 幂等检查今日签到及本人临期／到期状态；返回 unreadCount 和 serverTime，不修改阅读状态 |
| `GET /v1/messages?page=1&pageSize=20` | 返回 items、total、page、pageSize；上限100；按 createdAt DESC、id DESC；不生成签到消息 |
| `GET /v1/messages/unread-count` | 返回本人 unreadCount |
| `GET /v1/messages/:id` | 返回本人消息及最新业务状态，不隐式标记已读 |
| `PATCH /v1/messages/:id/read` | 幂等写入首次 readAt，返回更新后的消息及最新 action；不存在或非本人返回404 |
| `PATCH /v1/messages/read-all` | 单条带 userId 的更新语句标记操作处理时存在的未读消息，返回更新数量；随后刷新未读数 |
| `GET /v1/quest-records/:id` | 查询本人接取记录，供历史详情和提醒目标使用；不存在或非本人返回404 |

消息 items 字段为 `id,type,title,content,createdAt,readAt,businessStatus,signInDate,questRecordId,deadline,action`。action 为受控对象或 null，例如 `sign_in`、`continue_quest(recordId)`、`view_record(recordId)`；不接受外部 URL。签到当日未完成才可 sign_in；旧日已签显示已签到，旧日未签显示已过期。过期／结束任务可查看原记录，但不可继续任务。

扩展接取记录响应为可空 expiresAt、expiredAt 和新状态，保留原字段。保留现有记录查询默认 completed，允许显式 status=expired/abandoned/accepted；新增详情路由和消息静态路由须置于动态 id 路由之前。截止后完成／放弃返回409、code=QUEST_EXPIRED，前端据此刷新而非统一提示定位失败。

### 5. H5 交互与刷新

新增 `api/messages.ts`、`stores/messages.ts`、`MessagesView.vue` 和受保护 `/messages` 路由。技术默认入口为底部导航“消息”及未读角标（99以上显示99+，可访问标签保留真实数量），延续既有视觉样式。列表采用分页加载，提供全部已读、空态、错误重试和正在提交状态。

用户点击时先确认服务端标记已读成功，再根据返回的最新 action 导航；失败时保留原状态并提示重试。签到跳到 `/profile#daily-sign-in` 并定位现有组件；进行中任务跳到 `/today?recordId=...` 且加载后校验 activeRecord.id，一旦不匹配就查看原记录。新增 `/records/:id` 受保护详情页展示原接取记录，避免旧消息落到新的 active 任务。

`RecordsView.vue` 默认仍展示已完成纪念卡，增加过期记录筛选；任务详情覆盖完成、放弃、过期，过期记录不进入完成纪念卡和 completedCount。新接取任务显示绝对截止时间，旧记录隐藏期限提示。

登录恢复成功后同步消息；前台每30秒刷新消息未读数和当前 active 期限状态，跨日触发签到同步；页面隐藏暂停轮询，重新可见立即同步。签到、完成和放弃成功后刷新消息业务状态及未读数。轮询采用单一全局管理器，避免路由切换重复注册；登录用户变化或 auth:cleared 时清空并使旧请求响应失效。截止时前端禁用完成并刷新，最终以服务端为准。

### 6. 验证边界

以三个 specs 文件中的场景作为验收来源。后端用可控时钟覆盖北京时间跨日、提醒窗口和截止等号边界；MySQL 集成测试覆盖去重唯一键、并发接取、提醒／完成竞争、到期更新条件与用户隔离。保留签到积分事务回归。

前端验证点击与打开列表差异、全部已读、跨设备刷新、旧消息定向、账号切换丢弃旧响应、无权限／失败／空态，以及截止后返回409的正确提示。运行现有两仓构建、类型检查、相关自动化测试并记录浏览器手工验收；不把纯 mock 测试当作数据库并发已验证。

## Risks / Trade-offs

- [轮询与调度有短暂延迟] → 30秒周期、60秒正常目标，操作接口实时判断期限；不依赖定时器保护业务正确性。
- [消息持续增长] → 分页和索引、批量关联查询；第一版保留历史，后续清理策略单独提出，不自动删消息。
- [用户本地时间或多节点时钟偏差] → UTC 存储、服务端返回 serverTime、数据库最终条件与时钟同步；北京时间只用于签到业务日期。
- [过期与耗时外部校验竞争] → 最终条件更新再次检查期限，失败清理上传文件，任何终态不可覆盖。
- [已有工作区包含用户未提交修改] → 实现前核对签到、成长及相关测试的当前差异，只改本需求必要部分，禁止覆盖已有工作。
- [回滚旧后端会停止执行新期限] → 启用期限后采用保留期限执法能力的兼容回滚，不能将有截止时间的记录恢复为无限期；业务修复优先向前修复。

## Migration Plan

1. 实现阶段提供版本化向前 SQL、结构校验与回滚说明；备份后新增消息表、可空期限字段和索引。不更新旧记录数据，不启用生产自动同步。
2. 后端增加配置开关控制“新接取写期限”，默认关闭；已存在 expiresAt 的执法和后台处理不得被该开关关闭。先部署兼容新状态和接口的后端，验证旧记录仍无期限。
3. 部署可识别 expired 的 H5，再启用新接取期限。以开关启用为新旧接取分界；验证一条测试新记录的期限、临期提醒、到期名额和历史。正常使用不需要修改历史数据。
4. 未启用前可回滚应用并保留新增结构；启用后关闭新接取期限开关仅停止新增期限，继续处理已经产生的期限记录。回滚使用兼容版本，保留全部消息及期限数据，不在常规回滚中删除表、清空期限或复活过期记录。
5. 本阶段只交付规划；数据库脚本编写、部署与以上开关操作都属于后续实现／发布阶段。
