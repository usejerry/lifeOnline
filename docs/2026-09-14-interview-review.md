# 2026-09-14 后端知识复盘与面试表达

> 基于今天 LifeOnline 的消息中心、签到事务、BullMQ、Redis、MySQL 迁移和 Docker 部署实践整理。

## 一、今天完成了什么

今天的主线不是简单增加几个接口，而是把一个“每日签到提醒”需求拆成了完整的后端链路：

```text
BullMQ 定时调度
  -> Worker 分批查询当天未签到用户
  -> MessageService 持久化站内消息
  -> MySQL 唯一索引保证消息去重
  -> 鉴权接口分页查询、统计未读、标记已读
```

同时修正了签到与积分的事务边界：签到记录、成长积分余额、积分流水必须在同一个事务中完成，任何一步失败都整体回滚。

涉及的核心技术：

- NestJS 模块化、依赖注入、Guard、DTO 与 Pipe
- TypeORM Entity、Repository、EntityManager 和事务
- MySQL 唯一索引、外键、JSON、组合索引
- BullMQ 的 Queue、Job Scheduler、Worker、重试和退避
- Redis 持久化及容器化部署
- 时区与“时间点 / 业务日期”的区别
- 幂等、并发、游标分页和用户数据隔离
- 生产数据库迁移、备份、发布与回滚意识

## 二、最值得掌握的八个知识点

### 1. 为什么使用 BullMQ，而不是 `setTimeout` 或普通 cron

普通进程内定时器有明显限制：应用重启后状态丢失，多实例部署时每个实例都可能重复执行，也缺少任务状态、重试和失败记录。

BullMQ 将任务调度状态保存在 Redis 中，调度器负责按规则生成任务，Worker 负责消费。当前项目使用固定 scheduler ID 执行 `upsertJobScheduler`，多个应用实例启动时更新同一份调度计划，避免创建多份相同计划。

但要注意：队列不能天然保证业务“只执行一次”。网络中断、Worker 崩溃或重试都可能使任务再次执行，所以业务层仍必须实现幂等。

面试表达：

> 我们选择 BullMQ 是因为提醒属于异步、可重试的定时任务。Redis 保存调度和任务状态，应用重启后仍能继续处理。BullMQ 解决的是可靠调度和消费问题，数据库唯一索引解决的是业务重复写入问题，两者职责不同。

### 2. 幂等为什么必须依赖数据库约束

签到提醒的唯一约束是：

```text
(user_id, type, dedup_key)
```

签到消息的 `dedup_key` 使用业务日期；支线消息使用“任务记录 ID + 截止时间 + 提醒阶段”。即使两个 Worker 同时判断“消息不存在”，最终也只有一个 INSERT 能成功。

应用层的“先查再写”存在竞态：

```text
请求 A：查询不存在
请求 B：查询不存在
请求 A：插入成功
请求 B：再次插入
```

因此正确做法是让唯一索引成为最终防线。代码只捕获 MySQL 的 `ER_DUP_ENTRY`，将对应重复写转换为幂等成功；其他数据库错误继续抛出，不能吞掉。

面试表达：

> 幂等不能只靠查询判断，因为查询与插入之间存在并发窗口。我会设计稳定的业务幂等键，并用唯一索引兜底。命中重复键时返回已有记录，连接失败、字段错误等异常仍正常上抛。

### 3. 签到和积分为什么必须共用一个事务

签到包含三个相关写操作：

```text
写签到记录 -> 增加积分余额 -> 写积分流水
```

如果每个 Service 各自开启事务，内层积分事务可能已经提交，而外层签到失败，最终形成“没有签到记录但获得了积分”的不一致状态。

当前做法是由签到 Service 开启事务，将同一个 `EntityManager` 传给成长 Service，成长 Service 检测到已有 manager 后不再开启独立事务。积分余额和流水也使用这个 manager。

这是一种显式的事务传播方式。事务边界应由最了解完整业务流程的上层 Service 控制。

面试表达：

> 我把事务放在签到用例层，而不是每个表的 Service 内。下层方法支持接收 EntityManager，从而让签到、余额和流水共用同一连接与事务。任一步失败，异常抛出事务回调，TypeORM 会整体回滚。

### 4. 并发签到如何防止重复奖励

签到表具有组合唯一键：

```text
(user_id, check_in_date)
```

代码先查询可以快速处理常规重复请求，但真正防止并发重复签到的是唯一索引。如果两个请求同时通过查询，只有一个能插入，另一个命中 `ER_DUP_ENTRY` 并按“已经签到”处理，也不会继续增加积分。

这是“应用层友好判断 + 数据库最终约束”的组合。

需要继续思考的边界：如果未来使用 PostgreSQL，唯一键冲突会使当前事务进入失败状态，不能照搬 MySQL 中捕获异常后继续提交的写法，应改用 `ON CONFLICT DO NOTHING` 或单独设计事务流程。

### 5. 业务日期为什么不能直接用服务器本地时间

“2026-09-14”是签到业务日期，不是一个 UTC 时间点。服务器可能运行在 UTC，用户业务规则却要求按 `Asia/Shanghai` 跨日。

项目使用：

```ts
new Intl.DateTimeFormat('en-CA', {
  timeZone: 'Asia/Shanghai',
  year: 'numeric',
  month: '2-digit',
  day: '2-digit',
}).format(now);
```

需要区分：

- `created_at`、`read_at`、任务截止时间：表示时间轴上的时间点，统一按 UTC 存储和传输更合适。
- `check_in_date`：表示上海地区的业务日，应保存为 `DATE`。

面试表达：

> 时间点和业务日期是两类数据。时间点统一用 UTC，展示时再转换；签到日期按明确的业务时区计算并存 DATE，不能依赖服务器时区，否则换服务器或容器时区后会出现跨日错误。

### 6. 为什么批量扫描使用 ID 游标，而不是 offset

Worker 每批查询 200 个用户，并使用：

```text
WHERE user.id > lastUserId
ORDER BY user.id ASC
LIMIT 200
```

相比 `OFFSET n`，游标分页不会随着页数增大而不断扫描和丢弃前面的记录；执行期间有新用户插入时，结果也更稳定。

查询还使用 LEFT JOIN 找出当天没有签到记录的活跃用户，本质是 anti-join：关联结果为 NULL，说明不存在符合条件的签到记录。

需要注意：当前 Worker 对批次内用户逐个写消息，简单可靠，但吞吐量较大时可以使用有限并发或批量 INSERT；不能直接无限 `Promise.all`，否则会压垮数据库连接池。

### 7. 消息已读状态为什么用时间，而不是布尔值

`read_at IS NULL` 表示未读，非 NULL 表示已读。相比 `is_read`，时间字段不仅表达状态，还能回答“什么时候读的”，也能保留首次阅读时间。

单条已读更新条件同时包含：

```text
id + user_id + read_at IS NULL
```

作用有三个：

- `user_id` 防止修改其他用户消息；
- `read_at IS NULL` 保证重复请求幂等；
- 不覆盖已有时间，保留首次阅读时刻。

消息列表、未读统计和全部已读也始终带 `user_id`，这是多租户/用户数据隔离的基本要求。用户 ID 来自 JWT 上下文，而不是客户端请求体。

### 8. Entity 变更为什么还需要 SQL 迁移

开发环境可以临时使用 `DB_SYNCHRONIZE=true`，但生产必须是 `false`。原因是自动同步可能执行不可预期的删列、改类型或重建索引，缺少审核、备份和可控发布顺序。

生产发布正确顺序：

```text
检查代码与迁移
  -> 构建新镜像但暂不替换旧应用
  -> 备份数据库并验证备份
  -> 执行单个版本化迁移
  -> 核对真实表结构
  -> 启动新应用
  -> 查看日志并验证业务
```

迁移失败后不能想当然地直接重跑。MySQL 的很多 DDL 会隐式提交，必须先检查数据库已经执行到哪一步。

## 三、项目设计的关键取舍

| 问题 | 当前选择 | 原因 | 代价 |
| --- | --- | --- | --- |
| 定时提醒 | BullMQ + Redis | 可重试、可持久化、可观察 | 增加 Redis 运维成本 |
| 消息存储 | MySQL 持久化 | 支持历史、跨设备一致 | 数据持续增长，需要后续归档策略 |
| 重复消息 | 业务幂等键 + 唯一索引 | 抵抗并发和任务重试 | 幂等键设计必须稳定 |
| 扫描用户 | ID 游标分页 | 大数据量下比 offset 稳定 | 只适合基于稳定排序键向后遍历 |
| 已读状态 | `read_at` | 同时保存状态与时间 | 查询未读需合适组合索引 |
| 签到一致性 | 外层事务 + manager 传递 | 所有写操作原子提交 | Service 方法需要支持事务上下文 |
| 日期规则 | `Asia/Shanghai` 业务日 | 不依赖服务器时区 | 需要集中管理，避免各处重复实现 |
| 正式建表 | 显式 SQL 迁移 | 可审阅、可记录、可回滚评估 | 发布步骤比自动同步多 |

## 四、可直接用于面试的项目介绍

### 30 秒版本

> 我在 LifeOnline 中实现了站内消息和每日签到提醒。后端使用 NestJS、TypeORM 和 MySQL，定时调度使用 BullMQ 与 Redis。为了处理任务重试和多实例并发，我给消息设计了业务幂等键，并通过 MySQL 组合唯一索引保证最终不重复。扫描未签到用户时采用 ID 游标分页，业务日期统一按 Asia/Shanghai 计算。另外我把签到、积分余额和积分流水合并到同一个事务中，解决了部分成功导致的数据不一致问题，并补齐了生产迁移、Redis 配置和 Docker 部署流程。

### 2 分钟版本

> 这个需求表面上是每天定时提醒未签到用户，实际涉及调度可靠性、并发幂等、事务一致性、时区和生产发布。
>
> 调度方面，我使用 BullMQ Job Scheduler 创建每天执行的任务，Worker 从 Redis 获取任务后，按用户 ID 游标分批查询当天未签到的活跃用户。因为队列可能重试，而且多实例也可能并发处理，不能假设任务只执行一次，所以消息表使用用户、消息类型和业务幂等键组成唯一索引。重复插入时只识别唯一键冲突并返回已有消息，其他错误继续上抛。
>
> 数据一致性方面，原来的签到和积分分别提交，存在签到成功但积分失败，或者积分成功但签到失败的风险。我把事务边界提升到签到用例层，并把 TypeORM EntityManager 传入成长积分和流水逻辑，让三个写操作共同提交或回滚。签到表本身还有用户和业务日期的唯一约束，用来防止并发重复奖励。
>
> 最后，生产环境关闭 TypeORM 自动同步，通过显式 MySQL 迁移建表；部署时先构建、备份、迁移、核对结构，再启动新应用。同时在 Docker Compose 中补充 Redis 持久化、密码和健康检查。

## 五、高频追问与回答要点

### Q1：BullMQ 能保证任务只执行一次吗？

不能把它当成严格 exactly-once。分布式任务通常按至少一次的思路设计；Worker 失败、连接中断或重试都可能再次处理。业务侧要通过唯一索引、状态机或原子更新保证幂等。

### Q2：为什么不只使用 Redis 存消息？

Redis 更适合作为队列和临时状态存储；消息历史、分页查询、用户关联和长期一致性更适合 MySQL。Redis 数据丢失会影响待执行任务，但不应让已经生成的消息历史消失。

### Q3：先查询是否存在，再插入还不够吗？

不够。两个并发请求可能同时查到不存在。数据库唯一约束才是最终防线，先查主要用于减少常规重复请求的异常成本和返回更友好的结果。

### Q4：为什么不用 offset 分页？

深分页时数据库要扫描并丢弃大量前置行，数据变化时也容易重复或漏处理。后台全量扫描更适合使用单调递增 ID 作为游标。

### Q5：事务是不是越大越好？

不是。事务应覆盖必须原子完成的数据库写操作，同时尽量短。网络请求、地图服务或耗时计算不应放在长事务里，否则会增加锁持有时间、连接占用和死锁概率。

### Q6：如何验证事务真的回滚？

单元测试可以确认所有下层调用收到了同一个 manager、异常能抛出事务回调；但真正的提交、回滚和并发约束还需要 MySQL 集成测试，纯 mock 不能证明数据库行为。

### Q7：组合索引字段顺序怎么考虑？

先看实际查询条件和排序。消息常按用户隔离，再筛未读并按创建时间读取，因此索引从 `user_id` 开始，再考虑 `read_at`、`created_at`。不能只因为字段常用就机械地全部建单列索引。

### Q8：Redis 挂了会怎样？

Worker 和调度暂时不可用，签到提醒不会按时生成；MySQL 中已有消息和普通业务数据仍在。连接配置允许 Worker 等待 Redis 恢复，任务配置了有限重试和指数退避。生产上还应增加 Redis、队列积压和失败任务监控。

### Q9：为什么 Redis 不映射到公网？

Redis 只需要被应用容器访问，应通过 Compose 内部网络使用服务名 `redis:6379`。对公网开放 6379 会扩大攻击面；生产还应设置强密码、限制网络访问并持久化数据。

### Q10：为什么部署不能只执行 `docker compose restart app`？

restart 只重启旧容器，不会重新构建镜像，也不会加载容器创建后修改的环境变量。代码或依赖变更要重新 build/up，环境变量变更至少要 force-recreate。

## 六、当前实现中面试前必须主动校对的地方

这些不是知识点本身，而是当前仓库里容易被追问出矛盾的地方：

1. `DAILY_SIGN_IN_REMINDER_PATTERN` 当前为 `0 37 13 * * *`，实际是上海时间 13:37；scheduler ID 和部署手册写的是每天 20:00。上线和面试演示前必须统一。
2. OpenSpec 设计文档写明“不引入 Redis、消息队列”，实际代码已采用 BullMQ + Redis。应更新设计决策，明确为什么改变方案。
3. 规划文档包含支线到期、消息动态业务状态和前端交互，但当前提交主要完成消息基础接口与签到提醒。面试中要准确区分“已经实现”和“设计中的后续能力”。
4. 当前单元测试验证了 manager 传递和异常路径，但还没有证明真实 MySQL 下的并发、唯一约束与整体回滚。不要把 mock 单测描述成并发集成测试。
5. 时区格式化逻辑在签到 Service 和消息 Worker 中各有一份。后续可提取成共享工具，并用北京时间午夜边界的可控时钟测试覆盖。
6. `CreateMessageDto` 目前没有对外创建消息的 Controller 入口。若不准备开放用户创建消息，应删除未使用 DTO，避免让人误以为存在该接口。

## 七、建议补上的测试清单

- 同一用户同一天并发签到 10 次：只生成一条签到记录，只奖励一次积分。
- 积分余额更新或流水写入失败：签到记录、余额和流水都不落库。
- 同一提醒任务重复执行：只生成一条消息，已读时间不被重置。
- 两个 Worker 同时处理同一用户：唯一索引生效，任务整体不失败。
- 北京时间 23:59:59 与次日 00:00:00：业务日期正确切换。
- 用户 A 尝试读取或标记用户 B 的消息：返回不存在或无权限，数据不变化。
- 消息数量超过一批：游标扫描不重复、不漏用户。
- Redis 短暂中断后恢复：Worker 恢复消费，不产生重复业务消息。
- 迁移作用于包含旧数据的测试库：旧数据不变，表结构与 Entity 一致。
